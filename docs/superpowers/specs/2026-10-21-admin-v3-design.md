# Admin v3 — Design Spec

Date: 2026-10-21
Status: Approved in chat, pending written-spec review
Branch: `feat/futuristic-support-desk` (unmerged; DB work applies on the future dedicated Supabase project)

## Goal

Give staff a complete record of every customer interaction and the tools to act on it faster:
AI conversation log + weekly insights, AI draft replies/summaries, customer profiles,
agent availability with auto-assign, customer satisfaction (CSAT), and SLA escalation alerts.

## Constraints (all features)

- Every new table carries `organization_id` (directly or via ticket) and has RLS; anon never gets direct table access.
- Every new `public` function: `SET search_path = public`; `REVOKE ALL ... FROM PUBLIC, anon, authenticated` then explicit grants.
- Claude model `claude-opus-5-5`; no `thinking: disabled`, no forced `tool_choice`; refusal fallback `server-side-fallback-2026-07-01` + `fallbacks: "default"`.
- Photos are never stored (earlier decision A). Logs use `[photo]` markers + the AI's text.
- Pure logic lives in `src/lib/*` or `supabase/functions/_shared/*` with Vitest tests; SQL rules get assertions in `supabase/tests/*.sql`.

## 1. AI conversation log

**Table `ai_conversations`**

| column | type | notes |
|---|---|---|
| id | uuid pk | generated by the widget once per chat (`crypto.randomUUID()`) |
| organization_id | uuid fk organizations, not null | |
| transcript | jsonb not null | `[{role, content}]`, text only, `[photo]` markers |
| message_count | int not null | |
| first_question | text | first user message, ≤200 chars |
| ticket_id | uuid fk tickets null | set on handoff |
| created_at / updated_at | timestamptz | |

- Written only by `support-chat` (service role) after each successful AI reply: upsert by `id`; on conflict update only when `organization_id` matches (prevents cross-org overwrite).
- Widget sends `conversationId` with every `support-chat` request; validated as UUID.
- Handoff: `createHandoffTicket` passes `conversationId`; a `SECURITY DEFINER` RPC `link_ai_conversation(_conversation_id, _ticket_id, _token)` (anon) sets `ticket_id` when the ticket's `client_access_token = _token` and orgs match.
- RLS: select for org members (any role); delete for owner/admin; no insert/update policies.
- Admin page `/app/<slug>/ai-conversations` (owner/admin/agent; sidebar under CUSTOMERS): list (date, first question, message count, "→ Ticket"), text search (`ilike` on `first_question` and `transcript::text`), transcript drawer, delete (owner/admin, confirm).
- Ticket page: "View AI conversation" link when a conversation references the ticket.
- Widget footer note: "Chats are saved so our team can help you."

## 2. Weekly insights

- Table `ai_insights(id, organization_id, generated_at, period_start, period_end, themes jsonb, conversation_count int)`; RLS select org members; no client writes.
- Edge function `staff-ai` action `insights` (owner/admin only): loads last 7 days of `ai_conversations` (max 300, transcripts truncated to 1,500 chars each), asks Claude for JSON (structured output) `{themes: [{title, share_pct, count, examples: string[≤3]}]}` (≤6 themes), stores a row, returns it.
- Rate limit: refuse with 429 if the org's latest `generated_at` is < 1 hour ago.
- UI: panel at top of AI conversations page — latest insights (theme chips with % bars + examples), "Generate insights" button (owner/admin), "Last generated <time>".

## 3. AI draft reply & summary

- Edge function `staff-ai` (verify_jwt **true**), actions `draft_reply` and `summarize`, input `{ticketId}`.
  - Auth: user client from the request JWT; verify `has_org_role(ticket.org, ['owner','admin','agent'])` via RPC; else 403.
  - Context: ticket fields, `chatbot_transcript`, last 20 `chat_messages`, org canned responses (titles + bodies, ≤20).
  - `draft_reply`: returns `{draft}` (≤150 words, friendly, uses canned responses where relevant, never invents refund amounts/dates).
  - `summarize`: returns `{bullets: string[3]}` via structured output.
  - Shares the `bump_ai_chat_rate` limiter with key `staff:<user_id>`, 120/hour.
- UI (TicketDetails / TicketMessages): "✨ Draft reply" fills the reply textarea (never auto-sends; undo restores previous text); "Summarize" shows a dismissible 3-bullet card above the thread.

## 4. Customer profile

- Route `/app/<slug>/customers/:email` (all roles). Client names in TicketTable, LiveChats and AdminSuggestions link here.
- Data (existing tables, RLS-scoped): tickets by `email`, chat_messages of those tickets, ai_conversations linked to those tickets, suggestions by `author_email`.
- UI: header (name, email, counts: tickets/open/messages/suggestions, first seen), merged timeline newest first with typed icons, each linking to its source.
- Pure `buildCustomerTimeline(tickets, messages, conversations, suggestions)` with tests.

## 5. Agent availability & auto-assign

- Table `agent_presence(organization_id, user_id, status text check in ('online','away','offline'), last_seen_at, pk(organization_id,user_id))`.
  - RLS: org members select; a user may upsert only their own row (`user_id = auth.uid()` and member of org).
- Sidebar profile card: status dropdown; heartbeat upsert every 60s while the tab is visible; set `offline` on sign-out.
- Effective online = `status='online' AND last_seen_at > now() - 5 min`.
- RPC `org_agents_available(_org_id) returns boolean` (anon) for the widget header: "● AGENTS AVAILABLE" vs "Leave a message — we'll reply by email". Reveals only a boolean.
- Auto-assign: trigger BEFORE INSERT on `tickets` when `agent_requested_at IS NOT NULL AND assigned_to_user_id IS NULL`: pick effectively-online member with role owner/admin/agent and the fewest non-closed assigned tickets (tie → least recently assigned via `max(created_at)`); leave null if none.

## 6. Customer satisfaction (CSAT)

- Table `ticket_ratings(ticket_id pk fk tickets, score int check 1..5, comment text ≤1000, created_at)`.
  - RLS: org members select via ticket; no direct writes.
- RPC `rate_ticket_by_token(_token, _score, _comment)` (anon): ticket must match token and be `Resolved` or `Closed`; one rating per ticket (second call raises `already_rated`).
- RPC `get_ticket_by_token` unchanged; new `get_ticket_rating_by_token(_token)` returns `score` or null so the chat page knows to show stars.
- `/t/<token>` page: after resolution, a "How did we do?" card with 5 stars + optional comment; thank-you state after submit.
- Analytics: CSAT section — average (1 decimal), responses, 7-week trend, per-agent average (assigned_to_user_id). Pure `summarizeRatings(rows)` with tests.

## 7. SLA escalation alerts

- Bell: `StaffNotification.kind` gains `sla_at_risk` and `sla_breached`. Computed client-side from open tickets via `slaProgress` (≥0.75 → at risk, ≥1 or `sla_breached` → breached). Order: breached, agent_requested, at risk, client messages; newest first within kind.
- GHL: `pg_cron` job every 10 minutes runs `public.escalate_sla()`:
  - Table `sla_alerts_sent(ticket_id, level text in ('at_risk','breached'), sent_at, pk(ticket_id, level))`.
  - For open tickets with `resolution_due_at`, compute level; insert into `sla_alerts_sent` `ON CONFLICT DO NOTHING`; for each newly inserted row call `call_notify_webhook('sla_' || level, ticket_id, NULL)`.
  - `notify-webhook` accepts `sla_at_risk` / `sla_breached`; payload adds `assigned_to` (name, email) and `level`. Breached also sets `notify_owner: true` with owner email.
- Requires `CREATE EXTENSION IF NOT EXISTS pg_cron;` and `cron.schedule('escalate-sla', '*/10 * * * *', 'select public.escalate_sla()')`.

## Testing

- Vitest: timeline builder, ratings summary, SLA notification kinds/ordering, presence "effective online" helper, insights JSON parsing, staff-ai request validation, conversation ID validation, widget conversationId + footer, star rating component, draft-reply button behavior (fills, undo).
- SQL (`supabase/tests/admin_v3_checks.sql`): anon cannot read `ai_conversations`/`ai_insights`/`ticket_ratings`/`agent_presence`; cross-org isolation; `link_ai_conversation` wrong token rejected; `rate_ticket_by_token` rejects unresolved and second rating; presence upsert of another user denied; auto-assign picks least-loaded online agent and skips stale presence; `escalate_sla` sends once per level.
- Screenshots with mocked data for new pages.

## Build order

1 → 3 → 5 → 4 → 6 → 7 → 2

## Out of scope

- Storing photos; automatic log retention/deletion; per-agent working hours; email (non-GHL) SLA alerts; editing AI drafts with AI.

## Prerequisites

- Dedicated Supabase Pro project with `pg_net` and `pg_cron` enabled.
